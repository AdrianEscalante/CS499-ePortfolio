Artifact Description and Selection

The artifact I selected is the Warehouse Inventory Android application originally created for CS 360. Developed using Java, XML, and SQLite, the application supports user authentication, inventory management, CRUD operations, and low stock notifications.

I selected this application because it demonstrates multiple software development skills while providing opportunities to improve its original architecture, maintainability, and organization. Because the application was already functional, I could focus on improving the quality of the existing software rather than simply adding more functionality.

Architectural Improvements

During my code review, I identified that the original InventoryActivity handled too many responsibilities. In addition to managing the user interface, it communicated directly with DBHelper, processed SQLite Cursors, converted database records into InventoryItem objects, and performed inventory operations.

My primary enhancement was introducing an InventoryRepository class between InventoryActivity and DBHelper. Inventory operations, including retrieving, adding, updating, and deleting records, now pass through this repository.

I also moved Cursor processing into the repository, allowing InventoryActivity to focus on presentation rather than the details of SQLite data access. This reduced coupling and improved separation of concerns, making the application easier to maintain and expand.

Defensive Programming and Documentation

I strengthened input validation by explicitly rejecting negative inventory quantities before they reach the data layer. Although the Android interface already restricted certain invalid inputs, this additional validation ensures that business rules are not dependent entirely on the user interface.

I also improved documentation throughout the application. Rather than describing individual lines of code, my comments explain the purpose and responsibilities of classes, methods, and larger blocks of logic.

These improvements included documenting the repository layer, data processing responsibilities, input validation, RecyclerView behavior, and database operations. The changes make the application easier for other developers to understand while keeping documentation focused on the design and intent of the code.

Course Outcomes Demonstrated

This enhancement supports the third course outcome through evaluating the existing architecture and making design decisions based on software engineering principles. Introducing a repository adds another component to the application, but the tradeoff is reduced coupling and clearer separation between the presentation and data layers.

It also supports the fourth course outcome by applying established engineering practices to improve an existing solution while preserving its functionality. The repository pattern, defensive validation, and improved documentation provide a stronger foundation for future enhancements.

The additional input validation contributes to the fifth course outcome by demonstrating defensive programming and a more security conscious approach to handling application data.

Challenges and Reflection

One of the most important lessons I learned from this enhancement was the difference between functional software and software designed to remain maintainable as it grows.

When I originally developed the application, my primary concern was meeting the functional requirements of the CS 360 project. Revisiting the application during my capstone allowed me to evaluate the same code from a different perspective and recognize opportunities to improve its architecture.

The greatest challenge was modifying the application's architecture without breaking existing functionality. Moving database access and Cursor processing into InventoryRepository required evaluating which responsibilities belonged in each application layer.

I approached the enhancement incrementally and tested the application by adding, updating, and deleting inventory records after refactoring. These tests helped verify that the internal architecture had improved without affecting the original functionality.

Overall, this enhancement demonstrates how my approach to software development has evolved from simply making a program work to designing software that is easier to understand, extend, and maintain over time.

Artifact Description and Selection

The artifact I selected is the Warehouse Inventory Android application originally created during CS 360. The application was designed to allow users to manage inventory through basic functionality such as adding, updating, deleting, and viewing stored items. The original application also included user authentication and SMS alerts for low inventory.

I selected this artifact because it provides opportunities to demonstrate growth across all three enhancement categories in my ePortfolio. For this enhancement, I focused specifically on algorithms and data structures by improving how users search, organize, and prioritize inventory information.

Search and Sorting Enhancements

The first improvement involved implementing a search feature that allows users to search inventory records by name. I implemented a linear search that examines inventory items and compares their names against the user's search input.

I selected this approach because the current application manages a relatively small inventory. Linear searching also supports partial matches, allowing users to locate items as they type.

I also introduced several sorting options that allow inventory records to be displayed alphabetically, by quantity from lowest to highest, or by quantity from highest to lowest.

These improvements make the application more useful as the inventory grows. Users can quickly locate specific items and organize inventory information according to their immediate needs.

Priority Queue Implementation

The most significant data structure enhancement was introducing a restocking priority feature using Java's PriorityQueue.

I created a shared low stock threshold and used the priority queue to identify inventory items with quantities at or below that threshold. Items with the lowest quantities receive the highest restocking priority, allowing users to identify which products need attention first.

This functionality also works alongside the existing search feature. Users can search inventory records and then apply sorting or restocking logic to the filtered results.

To maintain separation of responsibilities, I created an InventoryAlgorithm class that handles these operations independently from the database layer.

This approach builds upon the architectural improvements established during my first enhancement and keeps the application organized as additional functionality is added.

Algorithm Efficiency and Design Decisions

This enhancement demonstrates the use of different algorithms and data structures depending on the problem being solved.

The application continues to use an ArrayList to maintain and display inventory records. Linear searching identifies matching items, comparators determine sorting order, and PriorityQueue organizes items according to their restocking priority.

An important design decision involved determining whether searching and sorting should occur through SQLite queries or within the application after retrieving inventory records.

Database processing could become more efficient if the application eventually manages significantly larger inventories. However, for the current scale, I selected in memory processing because it allowed the algorithms to remain reusable and demonstrated their implementation directly within the application.

The linear search has a time complexity of O(n), while comparison based sorting generally requires O(n log n) time. The priority queue provides an efficient way to repeatedly identify the next item requiring attention.

This enhancement directly supports the third course outcome by demonstrating the ability to design and evaluate computing solutions using algorithmic principles and appropriate data structures.

I evaluated multiple approaches to organizing inventory information and considered the tradeoffs between application level processing and database queries.

Challenges, Testing, and Reflection

The greatest challenge during this enhancement was ensuring that the new features worked together without disrupting existing functionality.

Implementing searching and sorting required maintaining a complete inventory list alongside a separate list containing the records currently displayed to the user.

This separation prevented searches from unintentionally operating on previously filtered results.

I also encountered implementation challenges involving Android layout constraints, imports, and connecting sorting options to the correct algorithm methods.

My testing approach involved rapid prototyping. I implemented each enhancement in small stages, tested the application after each change, and corrected issues before continuing to the next feature.

Overall, this enhancement improved both the functionality and quality of the Warehouse Inventory application.

Artifact Description and Selection

The artifact selected for this enhancement is my Warehouse Inventory Android application, originally developed during CS 360. The application allows users to create accounts, log in, and manage inventory records through a local SQLite database. Users can add, update, delete, and view inventory items while receiving SMS notifications when inventory reaches a low stock threshold.

During the previous two enhancements, I improved the application's software architecture and implemented searching, sorting, and restocking priority functionality. For this final enhancement, I focused specifically on database implementation. My goal was to improve reliability, preserve existing data during upgrades, and allow application settings to persist rather than remaining embedded within the Java source code.

Database Migration and Data Preservation

One of the most significant limitations of the original database implementation involved the way schema upgrades were handled. The original onUpgrade() method deleted the existing user and inventory tables before recreating them whenever the database version changed.

Although this approach satisfied the original course requirements, it would not be appropriate for a production application because upgrading the database could permanently erase user accounts and inventory records.

To address this issue, I increased the database version from one to two and replaced the destructive upgrade process with a migration that preserves existing data.

Instead of deleting existing tables, the migration creates a new app_settings table while leaving the original user and inventory records intact.

I tested this migration using information already stored in the application. After upgrading the database, I successfully logged into an existing account and accessed the same inventory records. This confirmed that the database structure could be expanded without losing existing data.

Persistent Application Settings

The new app_settings table also addressed another limitation of the original application. Previously, the low stock threshold used by the SMS notification system and restocking priority functionality was stored as a constant within the application code.

This design meant that changing the threshold would require modifying the source code and rebuilding the application.

The enhanced database now stores the low stock threshold as persistent information in SQLite. I implemented database methods for retrieving and updating the stored threshold and made these operations available through the InventoryRepository class.

This approach preserves the separation between the user interface and database operations established during the first enhancement.

Both the SMS notification logic and restocking priority algorithm now retrieve their threshold from the database instead of relying on constants defined within the application.

User Interface Integration

I also added a user interface option that allows the low stock threshold to be modified directly from the inventory screen.

Selecting the Set Low Stock Threshold button opens a dialog displaying the currently stored threshold and allowing the user to enter a replacement value.

After saving the new value, the application updates the SQLite database and immediately applies the updated threshold to its low stock functionality.

This improvement makes the application more flexible because different users and organizations may have different definitions of low inventory.

It also demonstrates communication between the user interface, repository layer, and persistent database storage. The resulting implementation provides a practical example of how application configuration can be managed through a database rather than source code.

Course Outcomes Demonstrated

This enhancement supports the computer science program outcome involving the application of established computing techniques, skills, and tools to develop solutions that provide practical value.

The database migration demonstrates consideration for data integrity and application reliability, while persistent configuration improves flexibility and maintainability.

By treating the database as more than a place to store inventory records, I expanded its responsibilities to include application configuration while preserving a clear separation between software components.

The implementation also establishes a foundation for future enhancements. Additional application settings could be introduced through the settings table without placing configuration values directly within the activity code.

Testing and Reflection

Testing focused on confirming that the database migration preserved existing information and that the new settings functionality operated correctly.

I verified that existing user accounts remained accessible after the database upgrade and that previously stored inventory records were still available.

I also tested the new threshold interface by updating the stored value and confirming that the application applied the new setting to its inventory functionality.

One of the most important lessons from this enhancement was understanding the importance of planning database changes around information that already exists.

A database upgrade should not simply create the desired structure. It should also preserve existing user information and maintain application functionality.

I also gained a stronger understanding of how persistent settings improve application flexibility and how database operations can be integrated without tightly coupling the user interface to SQLite implementation details.

Overall, this enhancement made the Warehouse Inventory application more reliable, configurable, and representative of the database development skills I have gained throughout my computer science program.
